# 发布守则

这份文件管的是"谁能在什么时候发布"，以及"发完怎么确认它真的发出去了"。
命令细节、踩过的坑在别处；这里只写**规则**，因为命令会变，规则不该变。

## 一、授权边界（硬性）

| 动作 | 谁能决定 |
| --- | --- |
| 改代码、本地 `git commit`、构建、截图 | 代理可自行完成，不用问 |
| `git push`、打标签并推送、建/改 GitHub Release、上传附件 | **必须先问，得到明确同意才执行** |

"或至少通知一声"不算同意。没批准就不推。

## 二、提交信息

只有两个词：首次 `Initial commit`，之后一律 `Update`。

- 不写 `feat:` / `fix:` / `chore:` 这类前缀，不写正文，不写多行。
- 更新内容写在 `CHANGELOG.md` 里（见下条），不进提交信息。

## 三、版本号与更新说明

- 版本号在四处重复：`package.json`、`src-tauri/tauri.conf.json`、
  `src-tauri/Cargo.toml`、`src/shared/about.ts`。改完必须跑
  `pnpm check:version`，不一致就别构建。
- **`pnpm check:version` 还要核对 `dist/` 里已构建前端的版本号**（2026-09-16 补）。
  起因值得记下来：Rust 侧构建用的是
  `tauri build --no-bundle --config '{"build":{"beforeBuildCommand":""}}'`，
  那串 `--config` **跳过了 `beforeBuildCommand`，而它正是 `pnpm build`（跑
  `vite build`）**。跳过之后 `dist/` 里上一次留下的前端会被**原样嵌进 exe**：
  v0.5.0 就这样把 0.4.5 的界面发了出去 —— 文件版本资源写着 0.5.0，设置窗口
  却印着 `v0.4.5`，用户点了「重启更新」也还是 0.4.5。
  **顺序永远是：先 `pnpm build`（前端），再 `tauri build`（Rust）。**
  `pnpm dist` 另外会检查 exe 是否比 `dist/` 旧，旧了直接拒绝出包。
- **`CHANGELOG.md` 是更新说明的唯一源头**。Release 页面的说明由它派生，
  不另写一份，避免两处慢慢说不到一块去。

### 发布说明的区间：上一次发布 → 这一次

**一次 Release 要交代的，是"上一次发出去的版本"到"这一次"之间的全部改动，
不是最后那个版本号底下的几行。**

中间那些只在本地提交、没打过标签（也就是没发过 Release）的版本，必须跟着本次
一起露脸。理由很直接：用户能装到的只有发出去过的版本，他从 v0.4.2 升到 v0.4.5，
中间的 v0.4.3、v0.4.4 他一个都没见过 —— 说明里漏掉，等于这批功能是"偷偷进来的"。

- 区间的起点由**标签**决定（标签 = 发出去过的版本），不由版本号决定。
- `pnpm release:notes` 会自动探测起点，收拢区间内所有版本的条目。
- 需要覆盖起点时用 `--since v0.4.0`；首次发布用 `--since none`。
- 自检的第 6 项会逐个核对区间内每个版本是否都出现在 Release 说明里，
  漏带任何一个都报 ❌ —— 这条就是专门用来抓"只写了当前版本"的。

### 发布说明的形态：合并成一份清单，不逐版本播报

**读者要的是"从上次发版到现在，这东西一共变成了什么样"，不是"每个版本号底下各干了什么"。**

所以说明里**不出现版本标题**，区间内所有条目按 **新增 / 改进 / 修复** 归到三类里。
更要紧的是：**同一处功能若被多个版本反复改动，要合并成一句**，只讲最终结果。

> 反例：v0.4.4 写"新增两个悬浮窗之间磁吸（阈值 14px）"，v0.4.5 又写"磁吸太紧、
> 拖不动，改 8px" —— 两段都摆出来，读者得自己拼出"所以现在到底能不能用"。
> 正解是合成一句：**新增两窗磁吸（吸力 8px，吸住后拨开 12px 松手，拖动跟手）**。

流程上是两遍：

1. `pnpm release:notes` 机械归并出**初稿**（按类别合并、每条前面留一行
   `<!-- vX.Y.Z -->` 注释标明出处，渲染时不显示）。
2. **人工再走一遍**：把同一主题的多轮改动合成一句，删掉不再成立的说法。
   脚本会在 stderr 列出"疑似讲的是同一件事"的条目对，照着改即可。

自检第 6 项会守住形态：说明里出现两个以上版本标题（`## 0.4.3` 这种）就报 ❌，
并粗查各版本谈过的主题是否还能在说明里找到（措辞可以重写，主题不该丢）。

## 四、发布流程

1. 先把功能改动 `git commit -m "Update"`（功能与版本号分开提交）。
2. 升版本号四处 + `CHANGELOG.md` 顶部加条目，跑 `pnpm check:version`。
3. 构建：**先 `pnpm build`（前端），再 `tauri build`（Rust）**，然后 `pnpm dist`
   把产物放到根目录 `WSight.exe`。脚本会打印大小和 sha256 —— 哈希留着，第 8 步
   回查要用；它还会拒绝"比前端还旧"的 exe。
   **顺序不能反、第一步不能省**：Rust 侧会把 `dist/` 原样嵌进去，跳过前端构建
   就是把上一个版本的界面打进这个版本的包里（见第三节）。
   **文件名固定不变**：程序是自替换更新，被替换的那个文件必须就是它自己运行的文件，
   固定名让开机启动项、快捷方式和替换动作都指向同一个路径。
4. **截图验收**：把 `opacity` 临时设为 1，启动程序截图，截完还原。
   编译通过不等于功能正常，看得见的这一遍不能省。
   **顺手看一眼设置窗口里的版本号**——它是"后端版本"和"前端版本"是否一致的
   唯一可见证据，v0.5.0 那次就是靠这一眼才发现的。
5. 提交版本变更，打标签 `vX.Y.Z`。
6. **征得同意后**推送 main 与标签。
7. 生成发布说明并建 Release：
   `pnpm release:notes` → **检查措辞、合并同主题条目** →
   `gh release create vX.Y.Z WSight.exe docs/*.png --notes-file …`。
   注意看它打印的"发布区间"与"覆盖 N 个版本"——数量不对就是漏带了。
8. **发版后自检**：`pnpm release:check`。全绿才算这一版发完了；
   有任何 ❌ 就当场处理，别留在下个版本。

### v0.5.0 起：发布页也是应用内的更新界面

程序自己会读 `releases/latest`，把**发布说明正文原样**显示成设置里的「本次更新内容」，
并下载附件里的 exe 来替换自己。于是发布页不只是给人看的网页，它同时是更新通道：

- **说明正文会出现在应用里**，用的是等宽纯文本（`<pre>`，没有 markdown 渲染）。
  所以写成 `- 一句话` 的清单最合适，别写只有开发者看得懂的措辞，
  也别放表格、图片引用这类在等宽文本里会散架的东西。
- **草稿与预发布版不会被推送**：更新器明确拒绝 `draft` 和 `prerelease`，
  正常的 `gh release create` 即可。
- **附件名必须是 `WSight.exe`**，且内容与本地 `pnpm dist` 打出的 sha256 一致：
  更新器会拿 GitHub 给的 `digest` 核对下载到的文件，对不上就丢弃。
  （老版本发布页没有 `digest` 时不至于失败，但界面会写明"仅核对文件大小"。）
- **忘了传附件 = 这个版本更新不了**（会报"这个版本没有附带 exe"），
  所以第 7 步的 `WSight.exe docs/*.png` 一个都不能少。

### v0.5.1 起：更新什么时候真正装上

下载完并不会自己就装，它会停在那儿等一个时机。时机有两个，走的是同一段代码
（`updater::apply`），差别只有一处——启动路径会把 `--startup` 传给新进程：

- **下次启动时自动装好**（默认路径）。程序在启动时、任何窗口出现之前，发现程序目录里
  有已下载并校验通过的 `WSight.exe.new`，就换上去、把控制权交给新版本，当前进程退出。
  用户下次开机就是新版，什么都不用做。
- **设置里点「重启更新」**。给想立刻生效的人用。

**为什么默认不能是"等用户点按钮"**：桌面组件的设置窗口基本没人会打开。只靠按钮的话，
更新包会下完往那儿一躺，一次都装不上——等于没有更新能力。而启动时换版那一刻很安全：
没有窗口、没有未保存的东西、也没人正看着。

**留一代旧版本做退路**。被换下来的 exe 改名成 `WSight-old-<版本>.exe` 保留，下一次更新
才清理掉（永远只留一代，不会一版堆一个）。名字带 `.exe` 是刻意的，理由见下面"回退"。

#### 回退：新版起不来怎么办

新版如果连窗口都起不来，就**没有任何界面能给出"回退"按钮**，退路只能是文件：

1. 进程序目录，把 `WSight-old-<上一版>.exe` 改名成 `WSight.exe`，覆盖掉起不来的那个。
   开机启动项、快捷方式指向的都是 `WSight.exe` 这个路径，这一改就稳定生效了。
2. 起来之后进设置点「忽略这个版本」，免得它把自己又装回来。

直接双击 `WSight-old-*.exe` 也能跑（用来快速确认旧版还正常），这类副本里**更新器整个停用**：
它存在的意义就是躲开某个版本，不该反过来把那个版本装回去。

如果失败的版本已经发出去了，正确做法是**从 GitHub 撤下这一版**或直接发修复版，
不是让每个用户各自回退。

#### 发之前必须真跑一遍升级

代价是坏版本会被静默装上，所以这条链路不能只靠读代码确认：
`.verify/verify_auto_apply.py` 会造一个"已下载待装"的更新包，启动程序，
确认它自己完成了替换、真正跑起来，而且旧版本被留成了 `WSight-old-*.exe`。
脚本全绿也仍然要在大王本机看一眼——几何、层级、外观这类毛病只有真桌面才算数。

### 补救：说明写漏了、或忘了合并

发布页的说明随时可以改，不用重发版本：

```bash
pnpm release:notes                        # 重新生成（会自动带上漏掉的版本）
# 手工把同主题的多轮改动合成一句
gh release edit vX.Y.Z --notes-file .verify/release-notes.md
pnpm release:check                        # 确认第 6 项转为 ✅
```

## 五、自检查什么

`scripts/post-release-check.mjs` 会回查远端（不只看本地命令的退出码）：

工作区是否干净、本地 HEAD 与远端 main 是否一致、远端最后一条提交说明是否合规、
标签是否指向 HEAD、Release 是否存在且附件齐全，以及第 6 项的三条：

- **说明覆盖了上一次发布到本次之间的每一个版本**（只报版本号都行，漏一个就 ❌）；
- **说明是归并稿**（出现两个以上版本标题说明还在逐版本播报，❌）；
- **说明与 CHANGELOG 同源**（各版本谈过的主题词在说明里找得到，找不到只警告 ——
  措辞本来就要重写，这条防的是"另写了一份"）。

设计意图很直白：**命令没报错 ≠ 发布成功**。附件漏传、标签打歪、提交说明手滑写成别的词、
说明漏带中间版本、说明还在逐版本播报，这些只有回头看一眼远端才能发现。

## 六、推送通道

只走 SSH，HTTPS 会被代理掐断（502）。推送时指定隧道配置，不要改全局 `~/.ssh/config`：

```bash
git -c core.sshCommand="ssh -F C:/Users/Administrator/.workbuddy/ssh_config_git" push origin main --tags
```

如果连不上，先确认 `~/.workbuddy/git-proxy-tunnel.py` 里的 `PROXY_PORT` 是系统代理端口
（`127.0.0.1:7897`），不要写沙箱注入的会话端口——那个端口每次会话都变。

## 七、已知隐患

`.github/workflows/release.yml` 在推送标签时会自动构建并尝试发布，但当前**每次都失败**：
`Resource not accessible by integration`（workflow 缺 `contents: write` 权限），
所以每个标签下面都留了一条红色的 Actions 记录。

**在它被修好或删掉之前，不要指望 CI 帮忙发版**——发布一律按上面第四节的流程手动做，
并且注意别让 CI 与手动发布抢同一个 Release。
